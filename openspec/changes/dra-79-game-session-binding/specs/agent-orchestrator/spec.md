## ADDED Requirements

### Requirement: Game-service calls stay bound to the agent session

Before forwarding a game-service MCP call that supplies a `session_id`, the agent-orchestrator SHALL compare that identifier with the calling agent session's stored `metadata.game_id`. When `metadata.game_id` is non-empty, the call SHALL be forwarded only when the supplied identifier names the same game. This check SHALL cover game actions, game-state reads, and turn or phase operations, and SHALL run before any game-service request or related state preflight.

A call that fails this binding check SHALL receive an error tool result generated by the orchestrator and SHALL NOT receive a downstream response or game state. The refusal SHALL NOT reveal whether the requested game exists or expose any of its state.

An agent session without a stored `metadata.game_id` SHALL retain first-call game discovery: its first successful game-service call SHALL be allowed, and the existing game identifier capture behavior SHALL bind the resulting game to that agent session.

#### Scenario: Bound session forwards a call for its own game

- **WHEN** an agent session stores game identifier `game-a` in `metadata.game_id` and a game-service tool supplies `session_id: "game-a"`
- **THEN** the orchestrator SHALL forward the call to game-service
- **AND** the call SHALL retain its supplied arguments

#### Scenario: Bound session rejects a different game before dispatch

- **WHEN** an agent session stores game identifier `game-a` in `metadata.game_id` and a game-service tool supplies `session_id: "game-b"`
- **THEN** the orchestrator SHALL return an error tool result without calling game-service
- **AND** the result SHALL contain no response or state from `game-b`

#### Scenario: Binding applies before state and turn preflight

- **WHEN** a bound agent session supplies a different game identifier to a game-service state-read, action, or turn-operation tool
- **THEN** the orchestrator SHALL reject the call before forwarding it or reading state for that requested identifier

#### Scenario: Unbound session discovers its first game

- **WHEN** an agent session has no stored `metadata.game_id` and its first successful game-service call supplies `session_id: "game-b"`
- **THEN** the orchestrator SHALL forward the call
- **AND** the orchestrator SHALL store `game-b` as that agent session's `metadata.game_id`

#### Scenario: Session metadata cannot rewrite the binding

- **WHEN** an ordinary session metadata update supplies a different `game_id`, `platform`, or restored context
- **THEN** the orchestrator SHALL ignore those client-supplied server-owned values
- **AND** the update SHALL preserve the session's existing values when they are present

#### Scenario: Concurrent prompts share one binding decision

- **WHEN** two jobs for the same agent session begin while its `metadata.game_id` is absent
- **THEN** the orchestrator SHALL serialize their prompt execution before either job's binding check
- **AND** after the first successful game call, the other job SHALL use the stored binding rather than select a second game

#### Scenario: Player agents inherit and retain the orchestrator binding

- **WHEN** an orchestrated session prompts a player agent
- **THEN** the parent session SHALL already have a non-empty `metadata.game_id`
- **AND** the player session SHALL be created or reused only when its game binding is absent or equal to the parent's binding
